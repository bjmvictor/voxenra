# 工作区保存与恢复审核

审核对象：v1.5.1 后的当前源码，2026-09-22。

## 结论

`.voxworkspace` 是引用原始影像的会话文件，不是包含影像的项目包。保存成功只表示状态文件写入成功，不代表原始影像已备份，也不表示保存时已重新验证每个源文件。

用户反馈的流程是“打开工作区 → 保存 → 退出 → 重开，提示一个序列缺失”，发生在另一台电脑。没有取得该工作区及源文件，尚不能确定该个案的原因。本次以普通 DICOM 文件和 ZIP 两类输入验证完整流程，重复恢复和保存两次，关闭控制器并清理所有会话解压目录，再用新的控制器打开，均成功。再次保存的来源清单与首次保存相同，没有写入新的临时解压路径。

## 实现流程

1. `WorkspaceDocumentController._capture()` 从主窗口和独立窗口收集页签，另收集左侧列表中的全部序列，生成纯数据快照。
2. `source_manifest()` 把压缩包解压文件映射回原始压缩包，记录来源路径及每个实例的身份、几何信息。
3. 后台线程编码 JSON，先写临时文件并刷新，再原子替换目标文件。不会把渲染对象或原始像素体积写入 JSON。
4. 打开时先校验格式，再按来源路径重新扫描 DICOM，逐一匹配保存的实例。
5. 检查通过后才替换当前工作区，依次加载页签和恢复状态。有缺失时保留当前工作区，等待重新定位、跳过或取消。

代码入口：

## 保存了哪些内容

| 类别 | 当前保存范围 |
| --- | --- |
| 来源 | 原始 DICOM 文件或外层压缩包路径；序列 UID；实例 UID、帧号、尺寸、位置、方向、像素间距等匹配信息 |
| 工作区 | 页签类型、标题、顺序、当前页签；左侧序列、选择、搜索、折叠状态、宽度；布局设置 |
| 2D | 切片、窗宽窗位、缩放平移、旋转翻转、反色、显示设置；多视口布局及显示模式 |
| MPR / 3D / 动态影像 | 切面位置、投影、联动、相机、显示参数、当前时相、播放模式与帧率；恢复后暂停播放 |
| 对比与融合 | 对比联动、CT/PET 显示参数、融合参数、配准矩阵和旋转中心 |
| 普通测量与标注 | 测量几何、所在图像平面、指标卡位置、已完成的文字和箭头标注；恢复时重新统计 ROI |
| 分割与体积编辑 | VOI 记录，包括持久化的二值分割掩膜及名称、颜色、可见性等；裁剪、去床掩膜和开关。掩膜采用压缩存储，依然依赖源影像 |

明确未保存或不能等同于保存的内容：

- 原始 DICOM 像素文件、缩略图和渲染缓存。
- **MTF、FWHM、Water QA 独立控制器的 ROI、分析结果及当前分析状态**；它们不属于普通测量快照。
- 撤销/重做历史、未完成的标注草稿、正在运行的任务。
- 独立窗口的精确位置；其页签恢复到主窗口。
- 设置/PACS/帮助等工具页内部的全部临时操作状态。
- 全部应用偏好：主题、语言、分析默认参数等保存在本机设置中；工作区仅复制布局设置。
- 外部导出的 PDF、CSV、SEG、SR 文件。已导入为内部 VOI 的分割掩膜则会随 VOI 保存。

自动恢复默认按 30 秒定时检查，在有未保存变更、存在工作内容且未忙碌等条件下写恢复副本。副本使用相同格式、同样引用原始影像，不能替代影像备份，也不直接覆盖手动保存的工作区。

## “一个序列缺失”的准确含义

当前提示把两类问题合并成“序列缺失或影像信息不一致”。计数单位是序列，并非页签或缺失文件数。一个序列只要有一个保存的实例无法匹配，整个序列就被判为缺失。

可能触发的情况：

- 路径已移动、重命名、删除，磁盘或共享目录不可访问。
- 原来从外部临时目录导入，文件在退出或系统清理后消失。
- 文件存在但不能被 DICOM 扫描器读取，或 UID、帧数、尺寸、位置、方向、像素间距等与保存时不一致。
- 只找回序列中的部分文件，或发生重复身份且无法唯一匹配。
- 旧版与当前版本的序列分组规则不同；代码已有部分旧版经典 MR 兼容处理，不能据此保证所有版本组合均兼容。

特别容易产生误解的行为：

1. 左侧列表中未打开的序列也会保存、校验，所以当前页签影像存在仍可能提示别的序列缺失。
2. 有相对路径时优先使用工作区旁的对应文件，否则使用绝对路径。相对路径仅在源文件位于工作区父目录之下时生成；不会自动搜索全盘。
3. 相对路径上的同名文件若存在但内容不匹配，目前不会再按身份回退尝试绝对路径上的另一份文件。
4. “保存成功”没有逐个检查源文件是否仍存在：内存中已载入的图像能够显示，但原始文件被移走后，下次仍无法恢复。
5. 手动选择文件夹或压缩包重新定位后仍要通过身份与几何校验；不会把不同影像强行套上原来的测量或分割。

因此，对另一台电脑上的问题，需要查看报错工作区记录的来源路径及对应文件状态才能区分具体原因；不能直接认定是压缩包来源追踪失效。

## 本次主题修复

- 为工作区的原生弹出窗口绑定主题底色，而不只修改 QML 内容背景。
- 将窗口加入已有的原生主题适配逻辑，保留系统标题及关闭按钮。macOS 使用对应 Aqua/DarkAqua 外观；Windows 复用已有 DWM 标题栏适配。
- 显式设置说明文本的选中背景及选中文字颜色。
- 检查打开状态下切换深浅主题、错误文字颜色，以及关闭后重新打开。

本机 macOS 原生窗口测试通过，实际 AppKit 外观与主题一致，原生标题保持可见。Windows 原生桌面效果仍需在 Windows 实机确认。

验证结果：工作区、恢复/退出、主题、分割持久化、窗口外观相关回归共 103 项通过、5 项平台相关测试跳过；另单独执行 macOS 原生主题测试，1 项通过。普通文件与 ZIP 的连续恢复/保存、退出清理解压目录、全新控制器重开均包含在回归中。

## 简化使用的建议（尚未实施）

建议保留一个工作区入口，主操作为“打开”“保存”；“另存为”提供便携保存选项。自动恢复作为辅助保障，不要求用户日常管理副本路径。

优先级：

1. **保存完整性与错误可解释性**：纳入 MTF/FWHM/QA 的 ROI 和分析状态，标明算法版本并在需要时重算；显示缺失序列名称、具体原因和文件数，支持选择一个根目录批量重新定位。
2. **便携工作区**：复制所需源影像并写相对引用，完成校验后再提交文件；与快速的引用式保存并存。无需把系统设置或无关的左侧影像默认打包。
3. **日常入口**：增加最近工作区；稳定显示工作区名称与保存状态，保留快捷保存。减少需要用户理解的“临时工作区”“恢复副本”等实现术语。

引用式保存适合本机持续工作，便携保存适合迁移或交接。界面应简短说明两种方式的文件大小与源影像依赖差异。
